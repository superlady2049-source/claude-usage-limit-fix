## 五、少做、少重复

1. 内部方案、没上线的东西只评审一轮，自己验收后定稿，不复验。
2. 最贵的模型只放在上线或交付前，几件合并评一次，同一件事最多 3 轮。
3. 脚本能判断的，人不再看；已测过的，不派 agent 重测。
4. 评审意见先合并再派修复，复验只做一轮。
5. 已有上下文的开发用续派接着做，不新开 agent；新 agent 只带三样：精简规则、本次数据、要回答的问题。
6. 能并行的一次派完，不多开 agent。
7. 内容先给使用者看，认可后才固化脚本和检查。
8. 先交能用的，文档规则跟在后面。

**评审用量分档（机器先上，人后上，越贵越晚上）：** 脚本检查（不耗 token）→ 自己看截图（约 2 万）→ 中档模型评审（10 万）→ 最强模型，仅口径或规则变更、上线前合并评（15 万）。前一档不过，不进下一档。

## 六、评审少走弯路（【实测】同一份交付连评 4 轮：58 → 66 → 74 → 66 分）

1. **先写「90 分长什么样」，再动手、再评审。** 把维度、每档标准、一票否决写成一页评分表；开发照着做，评审照着打分。没有标准就开评，每一轮都会冒出新的扣分点。
2. **评分分档写清楚**：底线、达标、优秀、杰出各写可验证的标准；没有证据的判定按低一档算。
3. **自报结果要用真实数据复核。** 开发用均摊出来的合成数据，自报召回 9/10；换成真实逐日数据，只有 5/7。验收集一律用真实数据固化成测试夹具。
4. **规则冲突本身就是 bug。** 加新规则时，同时删掉和它矛盾的旧规则；同一类错出现第二次，就写进钩子拦截（例如派活说明里出现「用到 N 万就停」直接拦下）。
5. **测试脚本也会误判。** 页面还在骨架屏就截图，会报「正文过短」；只看长度又会在正文没出来时放行。要等关键字出现，并且连续两次读到的长度不变。脚本第一次跑完，人工核对一遍结果。
